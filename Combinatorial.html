Architecture of an Operating System
Layered structure, components, and their applications in modern computing
OS Architecture — Layer Stack
Component Details & Applications
1. Hardware Layer
  • CPU: executes instructions; contains ALU (arithmetic), CU (control), registers, and on-chip cache (L1/L2)
  • RAM: volatile fast storage holding currently executing processes; typical sizes 4–256 GB
  • Application: the OS never modifies hardware directly — it issues commands via device drivers
  • DMA (Direct Memory Access): allows hardware (disk, GPU) to transfer data to/from RAM without CPU involvement, freeing the CPU for other tasks
2. Kernel (Core)
  • Runs in Ring 0 (most privileged CPU mode) — unrestricted hardware access
  • Monolithic Kernel (Linux, Unix): all OS services in one large process in kernel space → fast (no IPC needed), but unstable (one driver bug can crash everything)
  • Microkernel (Mach, QNX, Minix): only core (scheduling, IPC, memory) in kernel; everything else as user-space servers → stable and isolated, but slower due to context switching for IPC
  • Hybrid Kernel (Windows NT, macOS XNU): performance-critical parts in kernel, rest in user space; real-world compromise
  • Application: the kernel is what makes multi-tasking, security isolation, and hardware abstraction possible
3. System Call Interface
  • User programs cannot directly invoke kernel code — they use system calls (controlled entry points into the kernel)
  • CPU switches from User Mode → Kernel Mode via a software interrupt (INT 0x80 on x86, syscall on x86-64)
  • Process Control: fork(), exec(), wait(), exit(), getpid()
  • File Management: open(), read(), write(), close(), lseek()
  • Java relevance: FileInputStream.read() internally calls the C library read() which triggers a system call; new Thread().start() calls clone() or pthread_create()

Theoretical Content Details

An OS is the bridge between hardware and user applications. It is layered software — each layer abstracts the one below it and provides services to the one above.

Layers / Components
1. Hardware Layer
  • Physical components: CPU, RAM, ROM, Storage, I/O devices, NIC
  • The OS does not modify this layer — it only communicates through device drivers
  • Application: provides the raw compute and I/O capabilities everything else relies on
2. Kernel (Core of OS)
  • Runs in privileged/supervisor mode — has unrestricted hardware access
  • Responsible for: process management, memory management, I/O management, inter-process communication (IPC)
  • Two major types: Monolithic Kernel Microkernel
  • Monolithic Kernel (Linux, Unix) — entire OS runs in kernel space; fast but less stable (one bug can crash the system)
  • Microkernel (Mach, QNX) — only core services in kernel space; other services in user space; stable but slower (more context switching)
  • Hybrid Kernel (Windows NT, macOS XNU) — mix of both approaches
  • Application: the kernel is responsible for scheduling, virtual memory, file system access, and device I/O
3. Shell (Command Interface)
  • Provides the interface between the user and the kernel
  • Types: CLI (bash, cmd, PowerShell), GUI (Windows Explorer, macOS Finder)
  • Interprets user commands and converts them into system calls
  • Application: shell scripts automate system tasks; terminal emulators give developers raw system access
4. System Call Interface
  • System calls are the API through which user-space programs request kernel services
  • Categories: Process control (fork(), exec(), exit()), File management (open(), read(), write()), Device management (ioctl()), Information maintenance (getpid()), Communication (pipe(), socket())
  • Application: every time your Java program reads a file or opens a socket, it ultimately triggers a system call
5. User Space (Application Layer)
  • Where all user applications run — browsers, IDEs, databases, your Java programs
  • Runs in unprivileged mode — must request OS services via system calls
  • Cannot directly access hardware — maintains security and isolation
Key OS Subsystems
Process Manager
  • Creates, schedules, and terminates processes and threads
  • Maintains process states and context (via PCB — see PCB topic)
  • Handles inter-process communication and synchronization (semaphores, mutexes)
Memory Manager
  • Manages RAM allocation: virtual memory, paging, segmentation
  • Abstracts physical memory — each process sees its own virtual address space
  • Handles page faults, swap space, and page replacement algorithms (LRU, FIFO, Optimal)
File System Manager
  • Provides hierarchical namespace for files and directories
  • Manages storage allocation, file metadata (inode), access permissions
  • Examples: ext4 (Linux), NTFS (Windows), APFS (macOS)
I/O Manager
  • Abstracts I/O devices via device drivers
  • Manages I/O queues, buffering, and interrupt handling
  • DMA (Direct Memory Access) allows devices to access memory without CPU, improving throughput
Security and Access Control
  • User authentication, file permissions (read/write/execute), sandboxing
  • Privilege separation: user mode vs kernel mode prevents malicious code from accessing hardware

Process Control Block (PCB)
The data structure that represents the identity and state of a process

The PCB is the data structure the OS uses to store all information about a process. Every process has exactly one PCB. It is the "identity card" of a process.

Process Control Block (PCB) Structure
Contents of a PCB
1. Process Identification
  • PID (Process ID): unique integer identifier assigned by OS
  • Parent PID: PID of the parent process that spawned this one
  • User ID / Group ID: owner of the process — used for permissions
2. Process State
  • Current state: New, Ready, Running, Waiting, Terminated
  • The scheduler reads this to determine if the process is eligible for CPU time
3. CPU Registers (Context)
  • All CPU register values at the time of the last context switch: Program Counter (PC), Stack Pointer (SP), Accumulator, General Purpose Registers, Flags/Status Register
  • This is called the process context — saving and restoring this is a context switch
  • Application: without saving registers, a preempted process would lose its execution state permanently
4. Memory Management Information
  • Base and limit registers (for contiguous allocation)
  • Page table pointer (for paged memory systems)
  • Virtual-to-physical address mapping information
  • Application: allows the OS to isolate each process's memory — process A cannot access process B's pages
5. CPU Scheduling Information
  • Process priority (nice value in Linux)
  • Scheduling queue pointers (which ready queue it belongs to)
  • CPU burst history (used by algorithms like SRTF)
  • Time slice used / remaining
6. I/O Status Information
  • List of open file descriptors (file descriptor table)
  • I/O devices currently allocated to the process
  • Pending I/O requests
  • Application: when a Java program opens a FileInputStream, the OS adds an entry to this process's file descriptor table in the PCB
7. Accounting Information
  • CPU time used so far, wall clock time, time limits
  • Number of page faults, I/O operations performed
  • Application: OS uses this for billing in multi-user systems and for performance profiling
PCB in Different Scenarios
Context Switching
  • When the scheduler preempts process A to run process B: (1) Save all CPU registers of A into A's PCB. (2) Update A's state to Ready. (3) Load B's CPU registers from B's PCB. (4) Update B's state to Running.
  • This happens thousands of times per second — the OS must do it extremely fast
  • Java: each thread in JVM has its own mini-context; the JVM manages thread switching on top of OS process switching
Process Forking (fork())
  • OS creates a child process by duplicating the parent's PCB
  • Child gets a new PID; most fields are copied (memory maps, file descriptors, registers)
  • Java: Runtime.getRuntime().exec() and ProcessBuilder use this under the hood
Scheduling
  • Scheduler iterates through all PCBs in the ready queue, uses priority/burst time fields to decide which process runs next
Deadlock Detection
  • OS inspects the resource allocation fields in PCBs to build a resource allocation graph and detect cycles (deadlocks)

Theoretical Content Details
From Source Code to Execution
Stage 1: Writing Source Code
  • Developer writes human-readable code (e.g., Java source in .java files)
  • Code is stored on disk as plain text
Stage 2: Compilation
  • Java compiler (javac) converts .java → .class (bytecode)
  • Bytecode is platform-independent — not native machine code
  • C/C++ compilers convert source directly to machine code for a specific ISA (x86, ARM)
  • Phases: Lexical Analysis → Syntax Analysis → Semantic Analysis → Intermediate Code Generation → Optimization → Code Generation
Stage 3: Linking
  • Linker combines compiled object files + library references into an executable
  • Static linking: library code is embedded in the executable (larger but standalone)
  • Dynamic linking: libraries loaded at runtime from shared .so / .dll files (smaller executable, libraries shared among processes)
  • Java: ClassLoader performs dynamic linking at runtime, loading .class files on demand
Stage 4: Loading
  • OS loader reads the executable from disk into RAM
  • Allocates memory segments: code (text), data (static variables), stack, heap
  • Java: JVM is loaded first, then it loads the bytecode and interprets/JIT-compiles it
  • Sets up the program's virtual address space
Stage 5: Execution → Process
  • Once in memory and executing, the program becomes a process
  • OS creates a PCB for it, assigns a PID, and adds it to the ready queue
  • CPU executes instructions under OS scheduler control

Theoretical Content Details

The scheduler decides which process gets CPU time, for how long, and in what order. This is one of the most performance-critical components of the OS.

Non-Preemptive Scheduling

Once a process is given the CPU, it runs until it voluntarily relinquishes the CPU (by completing or doing an I/O wait). The OS cannot forcibly remove the process from the CPU.

1. First Come First Served (FCFS)
  • Simplest algorithm: processes are scheduled in the order they arrive in the ready queue (FIFO queue)
  • Non-preemptive: once a process starts, it runs to completion
  • Application: batch processing systems where jobs are submitted in order
  • Limitation Convoy effect: one long-burst process holds the CPU; all short processes wait — leads to very high average waiting time
  • Limitation Not suitable for interactive or real-time systems
2. Shortest Job First (SJF) — Non-Preemptive
  • The process with the shortest estimated CPU burst time is scheduled next
  • Provably optimal average waiting time among non-preemptive algorithms
  • Application: batch systems where job duration can be estimated (e.g., compilation jobs)
  • Limitation Starvation: long processes may never execute if short processes keep arriving
  • Limitation Burst time is unknown in advance — must be predicted (using exponential averaging)
  • Improvement over FCFS: eliminates convoy effect for short jobs
3. Priority Scheduling — Non-Preemptive
  • Each process gets a priority number; highest priority runs first (lower number = higher priority in most systems)
  • Application: OS kernel processes get higher priority than user processes
  • Limitation Starvation: low-priority processes may starve indefinitely
  • Solution to starvation: Aging — gradually increase priority of waiting processes over time
Preemptive Scheduling

The OS can forcibly remove a running process from the CPU and assign it to another. This requires saving the process context (via PCB) every time a preemption occurs.

4. Shortest Remaining Time First (SRTF) — Preemptive SJF
  • At every moment, the process with the shortest remaining burst time runs
  • If a new process arrives with a shorter remaining time than the currently running one, it preempts it
  • Application: time-sharing systems needing optimal response time
  • Difference from SJF: SRTF checks remaining time at every new arrival, not just at scheduling points
  • Limitation Very high context-switch overhead — preemption on every new arrival
  • Limitation Starvation of long processes persists
5. Round Robin (RR)
  • Each process gets a fixed time quantum (time slice, e.g., 10-100ms). When the quantum expires, the process is preempted and moved to the back of the ready queue (FIFO circular)
  • Designed specifically for time-sharing/interactive systems
  • Application: modern operating systems (Linux, Windows) use RR at the base level; CPU scheduling in JVM for threads
  • Improvement over FCFS: eliminates convoy effect; no process waits more than (n-1)*q time
  • Limitation If quantum is too small → too many context switches (overhead dominates). If too large → degenerates into FCFS
  • Limitation Average waiting time is often higher than SJF
6. Multilevel Queue Scheduling
  • Ready queue is split into multiple separate queues (e.g., foreground/interactive, background/batch)
  • Each queue has its own scheduling algorithm (RR for foreground, FCFS for background)
  • Fixed priority between queues: foreground always has priority over background
  • Application: modern OS — interactive processes run in a high-priority queue; batch/daemon processes in lower queues
  • Limitation Starvation of lower queues is possible
7. Multilevel Feedback Queue (MLFQ)
  • Extension of MLQ — processes can move between queues based on their behavior
  • CPU-bound processes that use their full quantum get moved to a lower-priority queue
  • I/O-bound processes (release CPU early) stay in high-priority queues
  • Aging can promote starved processes back up
  • Application: most modern OS schedulers (Linux CFS is inspired by this concept)
  • Improvement over MLQ: adaptive — doesn't need a priori knowledge of process type
  • Limitation Complex to configure (number of queues, quantum per level, aging threshold)

Theoretical Content Details
Pages and Paging
  • Physical memory (RAM) is divided into fixed-size blocks called frames
  • A process's virtual address space is divided into fixed-size blocks called pages (same size as frames, typically 4KB)
  • The OS maintains a page table per process: maps virtual page number → physical frame number
  • When a process accesses address X: CPU extracts page number, looks up frame in page table, computes physical address
  • Benefits: no external fragmentation; processes don't need contiguous physical memory; memory isolation between processes
Page in Memory (Page Hit)
  • When the process accesses a page that is already loaded in a physical frame
  • The page table has a valid bit = 1 for this page
  • Access proceeds normally — no OS intervention needed
Page Not in Memory — Page Fault
  • Process accesses a page not currently in RAM — valid bit = 0
  • Hardware raises a page fault interrupt
  • OS takes over: (1) Finds a free frame (or evicts one using page replacement algorithm). (2) Reads the required page from disk into the frame. (3) Updates the page table. (4) Resumes the process
  • This is expensive — disk access is 100,000x slower than RAM access
  • Page replacement algorithms: FIFO, LRU (Least Recently Used), Optimal (Belady's algorithm — theoretical)
Swap Space
Swap Out
  • When RAM is full and a new page is needed, the OS selects a page from RAM and writes it to a reserved area on disk called swap space (or page file in Windows)
  • The evicted page's frame is freed for the new page
  • The page table entry for the evicted page is updated: valid bit = 0, disk address recorded
  • Application: allows the system to run more processes than can fit in physical RAM (virtual memory)
Swap In
  • When a process needs an evicted page: page fault occurs → OS reads the page back from swap space into a free frame
  • The page table is updated: valid bit = 1, physical frame address set
  • Transparent to the running process — it doesn't know the page was evicted
Thrashing

Thrashing occurs when the OS spends more time swapping pages in and out than actually executing process instructions. CPU utilization collapses even though the system is "busy".

  • Cause: too many processes competing for too little physical memory — each process's working set doesn't fit in RAM
  • Symptom: high page fault rate, disk I/O at 100%, CPU utilization very low
  • Detection: page fault rate spikes while CPU utilization drops
  • Solutions: (1) Reduce degree of multiprogramming (suspend/swap out entire processes). (2) Use the Working Set Model — ensure each process has enough frames for its active working set. (3) Use page fault frequency (PFF) control: if PFF too high, give the process more frames; if too low, take frames away
  • Belady's Anomaly: in FIFO replacement, adding more frames can sometimes increase page faults (counterintuitive)
Cache: Hit and Miss
  • CPU cache (L1, L2, L3) sits between the CPU registers and RAM — much faster than RAM (L1: ~1ns, RAM: ~100ns)
  • Cache stores recently/frequently accessed memory blocks
Cache Hit
  • CPU needs data at address X — it is found in the cache
  • Data is returned from cache directly — no RAM access needed
  • Hit rate: fraction of accesses served from cache. High hit rate → near-RAM performance
Cache Miss
  • Data is not in cache — must be fetched from RAM (or disk if page fault)
  • Types of misses: Cold miss (first access — data never been cached), Conflict miss (two addresses map to same cache line), Capacity miss (working set larger than cache)
  • Cache miss penalty: performance degrades significantly on miss-heavy workloads
  • Java relevance: iterating an array sequentially has excellent cache performance (spatial locality). Accessing objects via random pointers has poor cache performance (pointer chasing)
TLB (Translation Lookaside Buffer)
  • A specialized cache for page table entries — caches virtual → physical address translations
  • TLB hit: translation found in TLB — fast memory access
  • TLB miss: OS must walk the page table in RAM to find the translation — slow

Theoretical Content Details

The disk arm (read/write head) must physically move to the correct track. Minimizing total head movement maximizes disk throughput. Disk scheduling decides the order in which pending I/O requests are serviced.

1. FCFS (First Come First Served)
  • Service requests in the order they arrive
  • Application: simple systems with light I/O load
  • Limitation Wildly varying head movement — no optimization; can cause extreme seek times
  • Baseline algorithm — all others improve on it
2. SSTF (Shortest Seek Time First)
  • Always service the request closest to the current head position next
  • Reduces total head movement significantly compared to FCFS
  • Application: workloads with requests clustered in certain disk regions
  • Improvement over FCFS: eliminates wild head movement; much better average seek time
  • Limitation Starvation: requests far from current head may never be serviced if closer requests keep arriving
  • Limitation Not optimal for worst-case scenarios
3. SCAN (Elevator Algorithm)
  • The disk arm moves in one direction servicing all requests along the way, reaches the end (or last request), then reverses direction and services requests on the way back
  • Like an elevator — it goes up servicing floors, reaches the top, comes back down
  • Application: heavily loaded disk systems — more predictable than SSTF
  • Improvement over SSTF: eliminates starvation — every request is eventually serviced
  • Limitation Requests just behind the head have to wait for a complete sweep — slightly unfair
  • Limitation Head always goes to the end even if no requests are there (wastes time)
4. C-SCAN (Circular SCAN)
  • Like SCAN but when the head reaches the end, it immediately returns to the beginning without servicing requests on the return trip
  • Treats disk as circular — uniform waiting time for all requests
  • Improvement over SCAN: fairer — avoids the situation where requests at the middle get serviced twice as often as those at the ends
  • Application: databases and file servers needing consistent I/O response times
  • Limitation More total head movement than SCAN (wasteful return trip)
5. LOOK and C-LOOK
  • LOOK: like SCAN but the head only goes as far as the last request in each direction (doesn't go all the way to disk edge)
  • C-LOOK: like C-SCAN but returns to the first request in the other direction (not disk edge)
  • Improvement over SCAN/C-SCAN: avoids unnecessary movement to disk edges — reduces total seek time
  • Application: modern operating systems (Linux uses a variant of LOOK)
  • Limitation Slightly more complex to implement than SCAN

Race Conditions & Synchronization
When concurrent processes access shared data and the outcome depends on execution order

A race condition occurs when multiple processes or threads read and write to shared data simultaneously, and the final result depends on the exact timing of their execution. This leads to unpredictable and incorrect behavior.

The Problem — Unsynchronized Access (Counter = 5)
The Solution: Synchronization
1. Critical Section Problem
  • A Critical Section is the part of code where shared resources are accessed.
  • To solve race conditions, we must ensure Mutual Exclusion: only one process can execute its critical section at a time.
  • Other requirements: Progress (processes aren't indefinitely blocked from entering if no one is inside) and Bounded Waiting (no starvation).
2. Synchronization Mechanisms
  • Mutex (Mutual Exclusion Lock): A simple locking mechanism. A thread acquires the lock before entering the critical section and releases it after. If another thread tries to acquire the lock, it is blocked until it's released.
  • Semaphores: A signaling mechanism using an integer variable. Binary Semaphores act like mutexes. Counting Semaphores allow a specific number of threads to access a resource pool (e.g., 5 available database connections).
  • Monitors: High-level abstraction provided by languages (like Java's synchronized keyword) that wrap data and operations, automatically acquiring and releasing locks.

Theoretical Content Details
1. Client-Server Architecture
  • Centralized model: dedicated server provides services; clients consume them
  • Server is always on, has a fixed address; clients can be intermittent and use dynamic IPs
  • Examples: Web (HTTP), Email (SMTP/POP3), DNS, Database servers
  • Application: most enterprise systems, web applications — easy to manage, secure, scalable with load balancing
  • Limitation Single point of failure (server down = service down). Server scalability bottleneck. High infrastructure cost.
2. Peer-to-Peer (P2P) Architecture
  • No dedicated servers — each node (peer) acts as both client and server
  • Peers communicate directly with each other; resources are distributed across all peers
  • Examples: BitTorrent, early Napster, blockchain networks, WebRTC
  • Application: file sharing, distributed computing (SETI@home), CDN augmentation
  • Advantage No single point of failure; scales automatically as more peers join; low infrastructure cost
  • Limitation Security/trust issues — peers are unknown. Performance inconsistent. Difficult to manage or enforce policies.
3. Hybrid Architecture
  • Combines client-server and P2P — a central server handles discovery/coordination; actual data transfer is P2P
  • Example: Skype (originally), Spotify (streams from server but some P2P for local network), modern gaming
  • Application: achieves the scalability of P2P with the organization of client-server
  • Limitation More complex to design and maintain
4. Three-Tier Architecture
  • Presentation Tier (UI/Client) → Application Tier (Business logic server) → Data Tier (Database server)
  • Example: Web application (Browser → Java Spring Boot Backend → PostgreSQL)
  • Application: enterprise web applications — separation of concerns, independent scaling
  • Limitation Increased latency (3 hops for every request); more complex deployment
5. Network Topology Types
  • Bus: all nodes share a single communication line. Simple but collision-prone; failure of bus = entire network down. Application: old Ethernet (10BASE2).
  • Star: all nodes connect to a central hub/switch. Easy to manage; failure of one node doesn't affect others; hub failure = total failure. Application: modern LANs.
  • Ring: nodes connected in a circle; data travels in one direction. Predictable performance; one failure breaks the ring. Application: Token Ring, SONET fiber rings.
  • Mesh: every node connected to every other. Highest redundancy; very fault tolerant. Application: backbone networks, military networks.
  • Tree/Hierarchical: hierarchical star topology. Application: corporate networks (core → distribution → access switches).

Subnet Mask
  • A 32-bit number that distinguishes the network portion from the host portion of an IP address
  • Network bits are all 1s; host bits are all 0s in the mask
  • Example: 255.255.255.0 = 11111111.11111111.11111111.00000000 → /24 → first 24 bits = network, last 8 bits = host
  • To find network address: bitwise AND of IP address and subnet mask
Default Gateway
  • The IP address of the router on the local network that handles traffic destined for other networks
  • When a device wants to reach an address outside its subnet, it sends the packet to the default gateway
  • The gateway router then forwards the packet toward the destination via routing tables
  • Example: Your PC is 192.168.1.100/24; default gateway is 192.168.1.1 (your router)
  • If you ping 8.8.8.8 (Google DNS), your PC sees it's outside 192.168.1.0/24 → sends to gateway → gateway forwards to ISP → ... → Google

Theoretical Content Details

The OSI (Open Systems Interconnection) model is a conceptual framework that standardizes how different systems communicate over a network. Each layer has specific responsibilities and communicates with the layer directly above and below it via defined interfaces.

Layer 7 — Application Layer
  • The layer closest to the end user — provides network services directly to user applications
  • Protocols: HTTP/HTTPS (web), SMTP/IMAP/POP3 (email), FTP (file transfer), DNS (name resolution), SSH, SNMP
  • Communication: provides data to Layer 6 (Presentation) for encoding; receives data from Layer 6 for display to user
  • Device interaction: web browsers, email clients, FTP clients operate here
  • Java relevance: HttpURLConnection, Socket, REST APIs, JDBC all operate at this layer conceptually
Layer 6 — Presentation Layer
  • Translates data between application format and network format: encoding, encryption/decryption, compression
  • Ensures data from Layer 7 is in a format the receiver's Layer 7 can understand
  • Examples: SSL/TLS encryption, JPEG/PNG image encoding, ASCII/Unicode translation, JSON/XML serialization
  • Communication: takes raw application data → formats/encrypts → passes to Layer 5; receives formatted data → decodes → passes to Layer 7
Layer 5 — Session Layer
  • Manages sessions (connections) between applications: establishes, maintains, synchronizes, and terminates sessions
  • Handles session checkpointing — allows transfer to resume after interruption
  • Protocols: NetBIOS, RPC (Remote Procedure Call), PPTP, SIP (VoIP signaling)
  • Communication: coordinates with Layer 4 to establish a reliable connection before data transfer begins
  • Example: a video call establishes a session — if it drops, the session layer can attempt reconnection
Layer 4 — Transport Layer
  • End-to-end delivery of data between applications (not just computers — specific ports)
  • Segmentation: breaks data from Layer 5 into segments; reassembles at the destination
  • Key protocols: TCP (reliable, ordered, error-checked, flow-controlled, connection-oriented) and UDP (unreliable, unordered, low-overhead, connectionless)
  • TCP: 3-way handshake (SYN → SYN-ACK → ACK), flow control (sliding window), congestion control
  • Port numbers identify specific applications (HTTP=80, HTTPS=443, SSH=22, MySQL=3306)
  • Communication: receives data from Layer 5 → segments it → hands off to Layer 3 with source/destination port in header
  • Java: java.net.Socket (TCP), java.net.DatagramSocket (UDP) operate at this layer
Layer 3 — Network Layer
  • Logical addressing and routing — gets data from source host to destination host across multiple networks
  • Uses IP addresses (logical addresses) for addressing; routers operate at this layer
  • Protocols: IPv4, IPv6, ICMP (ping), OSPF, BGP (routing protocols)
  • Fragmentation: if a packet is too large for the next link's MTU, this layer fragments it
  • Communication: receives segments from Layer 4 → adds IP header (source IP, destination IP) → creates a packet → passes to Layer 2
  • Device: Router reads the IP header at Layer 3 and makes forwarding decisions
Layer 2 — Data Link Layer
  • Node-to-node delivery — frames of data between directly connected devices on the same link
  • Uses MAC addresses (physical addresses burned into NIC) for addressing
  • Divided into: LLC (Logical Link Control) sublayer and MAC sublayer
  • Error detection: CRC (Cyclic Redundancy Check) in frame trailer
  • Protocols: Ethernet, Wi-Fi (802.11), PPP, ARP (resolves IP → MAC)
  • Communication: receives packets from Layer 3 → adds MAC header + trailer → creates a frame → passes to Layer 1
  • Devices: Switch (reads MAC addresses to forward frames), Network Interface Card (NIC)
Layer 1 — Physical Layer
  • Raw transmission of bits (0s and 1s) over the physical medium
  • Defines electrical, optical, or radio signal standards; cable types, connectors, voltage levels, bit timing
  • Examples: Ethernet cable (Cat5e, Cat6), fiber optic, Wi-Fi radio waves, Bluetooth
  • Communication: receives frames from Layer 2 → converts to electrical/optical/radio signals → transmits over medium; receives signals → reconstructs bits → passes to Layer 2
  • Devices: Hubs (physical repeaters), cables, modems, repeaters, antennas
How Two Devices Communicate (End-to-End)
  • Sender: Application data travels down all 7 layers — each layer adds its header (encapsulation): Data → Segment → Packet → Frame → Bits
  • At each intermediate router: bits → frame (L2) → packet (L3) → router reads IP, decides next hop → encapsulates in new frame → transmits
  • Receiver: bits travel up all 7 layers — each layer strips its header (decapsulation): Bits → Frame → Packet → Segment → Data → Application displays it
  • Peer-to-peer communication: each layer communicates logically with its peer layer on the other device using the protocol defined for that layer

Keys are attributes (or sets of attributes) that uniquely identify rows or establish relationships between tables. Understanding keys is fundamental to database design.

Super Key
  • Any set of one or more attributes that can uniquely identify a tuple (row) in a table
  • A super key may contain extra (redundant) attributes that are not needed for uniqueness
  • Example — Student table (StudentID, Name, Email, Phone): {StudentID}, {Email}, {StudentID, Name}, {StudentID, Email, Phone} — all are super keys as long as they uniquely identify a row
  • A super key with redundant attributes removed becomes a candidate key
  • Every candidate key, primary key, and unique key is also a super key — but not vice versa
Candidate Key
  • A minimal super key — no attribute can be removed without losing the uniqueness property
  • A table can have multiple candidate keys — all are equally valid candidates to be the primary key
  • Example: in Student table, both {StudentID} and {Email} could be candidate keys (assuming both are unique per student and neither can be further reduced)
  • Properties: Unique (no two rows have the same candidate key value) + Irreducible (minimal)
  • All candidate keys must be considered during database design
Primary Key
  • The candidate key chosen by the database designer to be the main unique identifier for a table
  • Rules: Must be unique. Must NOT be NULL (entity integrity). Should be stable (not change over time). Should be minimal (preferably a single column — surrogate key)
  • Example: StudentID INT PRIMARY KEY in SQL
  • The table can have only ONE primary key (but it can be composite)
  • Application: primary key values are used as foreign key references from other tables; all indexes typically built around PK; clustered index in most RDBMS is the primary key
  • Natural key vs Surrogate key: Natural key = real-world attribute (SSN, email). Surrogate key = system-generated (AUTO_INCREMENT ID). Surrogate keys are preferred for stability.
Foreign Key
  • An attribute (or set) in one table that references the primary key of another table
  • Enforces referential integrity: the foreign key value must either be NULL or exist as a primary key value in the referenced table
  • Example: Orders table has a CustomerID column that is a foreign key referencing Customers(CustomerID)
  • Actions on referenced record deletion/update: CASCADE (propagate change), SET NULL, SET DEFAULT, RESTRICT/NO ACTION (block the operation)
  • Application: foreign keys model real-world relationships (one-to-many, many-to-many via junction table); prevent orphan records
  • Java/JPA: @ManyToOne, @OneToMany, @JoinColumn annotations map to foreign key relationships
Composite Key
  • A primary key (or candidate key) consisting of two or more columns that together uniquely identify a row
  • Used when no single column is unique but the combination is
  • Example: Enrollment(StudentID, CourseID) — neither StudentID nor CourseID alone is unique, but their combination is (one student can enroll in one course only once)
  • The composite key is also a foreign key if each component references another table's primary key
  • Application: junction tables (bridge tables) in many-to-many relationships always have composite keys
  • Note Composite PKs make foreign key references from other tables more complex (must reference all components)

Theoretical Content Details

Normalization is the process of structuring a relational database to reduce data redundancy and improve data integrity. Each normal form eliminates a specific type of anomaly.

Types of Anomalies (why we normalize)
  • Insertion anomaly: can't insert data without inserting other unrelated data
  • Deletion anomaly: deleting one piece of data inadvertently deletes other data
  • Update anomaly: updating one piece of data requires updates in multiple rows (inconsistency risk)
First Normal Form (1NF)
  • Rules: (1) All attributes must be atomic (indivisible) — no repeating groups, no multi-valued attributes, no arrays in cells. (2) Each row must be uniquely identifiable (have a primary key).
  • Violation example: Student(StudentID, Name, Courses) where Courses = "Math, Physics, CS" — not atomic
  • Fix: create a separate row per course, or a separate Courses table
  • Application: without 1NF, SQL queries cannot work properly on sub-values within a cell
Second Normal Form (2NF)
  • Prerequisite: must already be in 1NF
  • Rule: No partial dependency — every non-key attribute must depend on the entire primary key (not just part of it). Applies only when the primary key is composite.
  • Violation example: OrderDetails(OrderID, ProductID, ProductName, Quantity) PK=(OrderID,ProductID). ProductName depends only on ProductID (not on OrderID+ProductID together) — partial dependency!
  • Fix: Move ProductName to a separate Products(ProductID, ProductName) table
  • Application: eliminates redundancy in tables with composite PKs; reduces update anomalies
Third Normal Form (3NF)
  • Prerequisite: must already be in 2NF
  • Rule: No transitive dependency — a non-key attribute must not depend on another non-key attribute. Every non-key attribute must depend directly on the primary key.
  • Violation example: Employee(EmpID, DeptID, DeptName) — DeptName depends on DeptID (not on EmpID directly). DeptID → DeptName is a transitive dependency.
  • Fix: Create Department(DeptID, DeptName) table; Employee only keeps DeptID as foreign key
  • Application: 3NF is the standard target for most production databases — balances normalization with query performance
Boyce-Codd Normal Form (BCNF)
  • Prerequisite: must already be in 3NF
  • Rule: Stricter than 3NF — for every non-trivial functional dependency X → Y, X must be a superkey. Eliminates anomalies that 3NF misses when there are multiple overlapping candidate keys.
  • Violation example: StudentCourse(StudentID, Course, Professor) where each professor teaches only one course (Prof → Course) but a student can take multiple courses. Professor → Course but Professor is not a superkey → BCNF violation.
  • Fix: Decompose into ProfCourse(Professor, Course) and StudentProf(StudentID, Professor)
  • Application: critical when table has multiple candidate keys that overlap — BCNF guarantees no anomalies for FD-based redundancy
  • Note BCNF decomposition may not always preserve all functional dependencies (lossless join but not always dependency-preserving)
Fourth Normal Form (4NF)
  • Prerequisite: must already be in BCNF
  • Rule: No multi-valued dependencies (MVD). If A →→ B (A multi-determines B), then A must be a superkey.
  • Multi-valued dependency: an attribute independently determines a set of values for another attribute
  • Violation example: Employee(EmpID, Skill, Language) — an employee has multiple skills AND multiple languages, independently. EmpID →→ Skill and EmpID →→ Language. Combining them causes redundancy (every skill paired with every language).
  • Fix: Decompose into EmpSkill(EmpID, Skill) and EmpLanguage(EmpID, Language)
  • Application: eliminates spurious combinations caused by independent multi-valued facts; important for HR, product catalog (product with multiple colors and multiple sizes)
Fifth Normal Form (5NF) — Project-Join Normal Form (PJNF)
  • Prerequisite: must already be in 4NF
  • Rule: No join dependencies that are not implied by candidate keys. A table cannot be reconstructed from its projections unless those projections are based on candidate keys.
  • Deals with cases where a table can be decomposed into three or more smaller tables but cannot be decomposed into just two without losing information
  • Very rare in practice — found in complex many-to-many-to-many relationships
  • Application: complex enterprise schemas — inventory (Supplier, Part, Project) where the relationship is a three-way constraint
  • 5NF ensures the decomposition is lossless even for complex multi-join scenarios

Theoretical Content Details
What is a Transaction?
  • A transaction is a sequence of one or more database operations (reads/writes) that are treated as a single logical unit of work
  • Either ALL operations in a transaction succeed and are permanently recorded, OR NONE of them take effect (all-or-nothing)
  • Example: Bank transfer — debit account A AND credit account B. These two operations must be one transaction. If debit succeeds but credit fails, money disappears. The transaction ensures both happen or neither happens.
  • SQL: BEGIN TRANSACTION; ... COMMIT; (or ROLLBACK;)
  • Java: JDBC connection.setAutoCommit(false); ... connection.commit(); / connection.rollback();
ACID Properties
A — Atomicity
  • "All or Nothing" — a transaction is an atomic unit; either all its operations complete successfully, or none of them take effect
  • If any operation in the transaction fails (network error, constraint violation, application crash), the system rollbacks all previous operations in that transaction
  • Implemented by: undo logs (the DBMS records what each operation changed so it can undo them); write-ahead logging (WAL)
  • Example: e-commerce order placement — create order record + deduct inventory + charge payment card. If payment fails, the order and inventory changes must be rolled back.
C — Consistency
  • A transaction must take the database from one valid, consistent state to another valid, consistent state
  • All defined rules (constraints, triggers, cascades) must be satisfied before and after the transaction
  • Consistency is partially the developer's responsibility (write correct transaction logic) and partly enforced by the DBMS (constraints: NOT NULL, UNIQUE, FK, CHECK)
  • Example: a banking transfer must not violate the constraint that account balance cannot go negative (if that's a rule). If it would, the transaction is rolled back.
I — Isolation
  • Concurrent transactions must execute as if they were running serially — one at a time. Intermediate states of a transaction are not visible to other concurrent transactions.
  • Without isolation: dirty reads (reading uncommitted data), non-repeatable reads (same query returns different results within one transaction), phantom reads (new rows appear in repeated query)
  • Isolation levels (weakest to strongest): Read Uncommitted → Read Committed → Repeatable Read → Serializable
  • Higher isolation = fewer anomalies but lower concurrency (more locking)
  • Implemented by: locking (2-phase locking, row-level locks) or MVCC (Multi-Version Concurrency Control — PostgreSQL, InnoDB)
  • Java: connection.setTransactionIsolation(Connection.TRANSACTION_REPEATABLE_READ);
D — Durability
  • Once a transaction is committed, its changes are permanently recorded and will survive system failures (crashes, power loss)
  • Implemented by: write-ahead log (WAL) — changes are written to a durable log on disk before being committed. On crash recovery, the DBMS replays the log.
  • Application: ensures data integrity after commit — when the customer sees "Payment successful", it will not be lost even if the server crashes 1 second later

Deadlocks in Transactions
When transactions wait indefinitely for each other to release locks

A deadlock occurs when two or more transactions form a cycle of dependencies, each waiting for the other to release a lock on a resource. Without intervention, they will wait forever.

Deadlock Cycle (Wait-For Graph)
Handling Deadlocks
1. Deadlock Detection & Resolution
  • The DBMS periodically builds a Wait-For Graph (like the diagram above) where nodes are transactions and directed edges are dependencies.
  • If a cycle is detected, a deadlock exists.
  • Resolution: The DBMS automatically aborts (rolls back) one of the transactions (the "victim"). The other transaction proceeds. The victim is usually restarted automatically.
2. Deadlock Prevention
  • Resource Ordering: Force all transactions to acquire locks in the same specific order (e.g., alphabetical order of tables/rows). If everyone locks Row 1 before Row 2, cycles cannot form.
  • Wait-Die Scheme (Non-preemptive): Older transactions can wait for younger ones. Younger transactions must abort instead of waiting for older ones.
  • Wound-Wait Scheme (Preemptive): Older transactions preempt (abort) younger ones. Younger transactions can wait for older ones.
Application & Best Practices:

Deadlocks are normal in highly concurrent SQL databases (like Postgres or MySQL). You cannot completely prevent them without crippling performance. The standard engineering practice is to catch the Deadlock Exception in your application code and simply retry the aborted transaction.

OOP is a programming paradigm that organizes code around objects — instances of classes that bundle data (state) and behavior (methods) together. Java is a class-based, object-oriented language.

1. Encapsulation
  • Bundling data (fields) and the methods that operate on that data into a single unit (class), and restricting direct access to internal data from outside the class
  • Achieved via access modifiers: private (class only), default (package), protected (package + subclasses), public (everywhere)
  • Data is kept private; access is provided via public getter/setter methods — the class controls how its data is accessed and modified
  • Benefits: hides internal implementation (information hiding); controls data validation in setters; allows changing internal implementation without breaking external code
  • Java example: A BankAccount class with private double balance and a public void deposit(double amount) method that validates the amount before modifying balance
2. Inheritance
  • A class (subclass/child) acquires the fields and methods of another class (superclass/parent), extending and specializing its behavior
  • Java: class Dog extends Animal — Dog inherits all non-private members of Animal
  • Single inheritance only in Java for classes (a class can extend only one class); multiple inheritance via interfaces
  • IS-A relationship: a Dog IS-A Animal; a Car IS-A Vehicle
  • Benefits: code reuse (don't rewrite Animal's breathe() method in Dog); hierarchical classification; polymorphism enablement
  • super keyword: calls the parent class's constructor or method from the subclass
  • final class: cannot be extended (e.g., String in Java is final)
  • Important Prefer composition over inheritance when the relationship is HAS-A not IS-A (e.g., Car HAS-A Engine, not Car IS-A Engine)
3. Polymorphism
  • "Many forms" — the same method name/interface can behave differently depending on the object type
  • Compile-time polymorphism (Method Overloading): multiple methods with the same name but different parameter lists in the same class. Resolved at compile time. Example: add(int a, int b) and add(double a, double b)
  • Runtime polymorphism (Method Overriding): a subclass provides a specific implementation for a method already defined in its superclass. The method called depends on the actual object type at runtime, not the reference type. This is Dynamic Method Dispatch.
  • Example: Animal a = new Dog(); → a.speak() calls Dog's speak(), not Animal's. The JVM determines the correct method at runtime via the vtable (virtual method table).
  • Rules for overriding: same method signature (name + parameters); return type must be same or covariant; cannot reduce visibility; @Override annotation recommended
  • Benefits: extensibility — add new subclasses without changing existing code; write code against interfaces/superclasses
4. Abstraction
  • Hiding complex implementation details and exposing only the essential interface to the user
  • Focuses on WHAT an object does, not HOW it does it
  • In Java: achieved via Abstract Classes and Interfaces
  • Abstract Class: declared with abstract keyword; may have abstract methods (no body) and concrete methods; cannot be instantiated. Subclasses MUST implement all abstract methods.
  • Interface: a contract — defines method signatures that implementing classes must provide; all methods are implicitly public abstract (pre-Java 8); from Java 8, can have default and static methods; from Java 9, private methods
  • Abstract class vs Interface: use abstract class for IS-A with shared state/implementation; use interface for capability contract (CAN-DO) or when multiple inheritance is needed
  • Example: interface Drawable { void draw(); } — a Circle, Rectangle, and Triangle all implement Drawable differently, but client code just calls shape.draw()

Theoretical Content Details
Class and Object
  • Class: blueprint/template defining attributes (fields) and behaviors (methods). A class is a user-defined data type.
  • Object: an instance of a class created at runtime with its own state. Multiple objects of the same class have the same structure but different data.
  • Java: Dog rex = new Dog(); — Dog is the class; rex is the reference variable; new Dog() creates the object on the heap
Constructor
  • Special method called when an object is created — initializes the object's state
  • Same name as class, no return type
  • Types: default constructor (no-arg, provided by compiler if none defined), parameterized constructor, copy constructor (not built-in in Java — manually implemented)
  • Constructor chaining: this() calls another constructor in the same class; super() calls parent's constructor (must be first statement)
this Keyword
  • Refers to the current object instance inside an instance method or constructor
  • Uses: disambiguate field from parameter (this.name = name), call another constructor (this()), pass current object as argument
static Keyword
  • Static members belong to the class, not to any specific instance
  • Static fields: shared across all instances (Student.count)
  • Static methods: can be called without creating an object; cannot access instance (this) fields
  • Static initializer block: runs once when class is first loaded
  • Static nested class: does not have access to instance members of outer class
final Keyword
  • final variable: constant — value cannot be changed after assignment
  • final method: cannot be overridden by subclasses
  • final class: cannot be extended (subclassed). Example: String, Integer, Math

Java Execution Architecture
JVM Memory Explained
  • Heap: all objects created with new reside here. Shared across all threads. Subject to GC. Divided into Young Generation (Eden+Survivor S0,S1) and Old Generation (Tenured)
  • Stack: each thread gets its own stack. Contains frames — each method call creates a frame with local variables, operand stack, and return address. LIFO. StackOverflowError on deep recursion
  • Metaspace (Java 8+, replaced PermGen): stores class metadata, method bytecode, static fields. Grows dynamically (no fixed PermGen size). Can trigger OutOfMemoryError: Metaspace
  • String Pool: a special region in the heap where string literals are interned. "hello" == "hello" is true (same pool object). new String("hello") bypasses pool.
  • PC Register: per-thread program counter pointing to current bytecode instruction
Java Specifics (Theoretical Details)
Java Architecture
Platform Independence — "Write Once, Run Anywhere"
  • Java source (.java) → compiled by javac → bytecode (.class) → executed by JVM
  • Bytecode is platform-independent — the JVM interprets it and translates to native machine code for the specific OS/CPU
  • JVM implementations exist for Windows, Linux, macOS, Android — same bytecode runs on all
JVM (Java Virtual Machine)
  • An abstract computing machine that executes Java bytecode
  • Components: Class Loader (loads .class files on demand), Bytecode Verifier (security check), Execution Engine (Interpreter + JIT compiler), Garbage Collector, Runtime Data Areas
  • JIT (Just-In-Time) Compiler: identifies "hot" bytecode paths executed frequently → compiles them to native machine code at runtime for near-native performance
JVM Memory Areas
  • Heap: all objects created with new are stored here. Shared across all threads. Managed by Garbage Collector. Divided into Young Generation (Eden + Survivor) and Old Generation (Tenured).
  • Stack: each thread has its own stack. Stores stack frames — each method call creates a frame with local variables, parameters, return address. LIFO structure. Stack overflow → StackOverflowError
  • Method Area (Metaspace in Java 8+): stores class metadata, static variables, constant pool, method bytecode. Shared across threads.
  • Program Counter (PC) Register: per-thread register pointing to the currently executing instruction
  • Native Method Stack: for native (C/C++) method calls via JNI
JDK vs JRE vs JVM
  • JVM: runs bytecode — the runtime engine
  • JRE (Java Runtime Environment): JVM + standard libraries (java.lang, java.util, java.io, etc.) — needed to run Java programs
  • JDK (Java Development Kit): JRE + development tools (javac compiler, javadoc, debugger, jconsole) — needed to develop Java programs
Java Key Theoretical Concepts
Garbage Collection
  • Java automatically manages heap memory — the GC identifies and reclaims objects no longer reachable by any live thread
  • No manual malloc/free like C — eliminates dangling pointers and most memory leaks
  • GC algorithms: Serial GC, Parallel GC, CMS (deprecated), G1 GC (default since Java 9), ZGC, Shenandoah
  • GC roots: static fields, local variables on stack, active threads — objects reachable from roots are live; others are collected
  • Generational GC: young objects die quickly (Minor GC in Young Gen is fast); long-lived objects promoted to Old Gen (Major/Full GC is slower)
  • Developers cannot force GC (System.gc() is a hint, not a command)
Java Data Types
  • Primitive types: stored directly on the stack (or in object fields on heap). 8 types: byte(1B), short(2B), int(4B), long(8B), float(4B), double(8B), char(2B), boolean(1b)
  • Reference types: variables hold a reference (pointer) to an object on the heap. Classes, arrays, interfaces, enums.
  • Autoboxing/Unboxing: automatic conversion between primitives and their wrapper classes (int ↔ Integer, double ↔ Double) — introduced in Java 5
String in Java
  • String is immutable — once created, its value cannot be changed. Any modification creates a new String object.
  • String Pool (interning): Java maintains a pool of String literals in the Method Area. "hello" == "hello" is true (same pool object); new String("hello") == new String("hello") is false (different heap objects)
  • Use .equals() for content comparison, never == for Strings
  • For mutable string operations: StringBuilder (single-threaded, fast) or StringBuffer (thread-safe, slower)
Exception Handling
  • Java uses a hierarchy: Throwable → Error (JVM-level, unrecoverable: OutOfMemoryError, StackOverflowError) and Exception (recoverable)
  • Checked exceptions: must be declared (throws) or caught. Compiler enforces this. Example: IOException, SQLException
  • Unchecked exceptions (RuntimeException): not required to be caught/declared. Example: NullPointerException, ArrayIndexOutOfBoundsException, ClassCastException
  • try-catch-finally: finally block always executes (cleanup). try-with-resources (Java 7+): auto-closes AutoCloseable resources
Java Collections Framework (theoretical)
  • Hierarchy: Collection interface → List (ordered, allows duplicates), Set (no duplicates), Queue. Map (key-value, separate hierarchy)
  • List implementations: ArrayList (dynamic array — O(1) random access, O(n) insert/delete in middle), LinkedList (doubly linked — O(n) access, O(1) insert/delete with iterator)
  • Set implementations: HashSet (O(1) ops, no order), LinkedHashSet (insertion order), TreeSet (sorted, O(log n))
  • Map implementations: HashMap (O(1) avg, no order), LinkedHashMap (insertion order), TreeMap (sorted keys, O(log n))
  • Thread-safe alternatives: ConcurrentHashMap, CopyOnWriteArrayList, Collections.synchronizedList()
Java Multithreading (theoretical)
  • A thread is the smallest unit of execution. Java's Thread class and Runnable interface allow multi-threaded programs.
  • Thread lifecycle: New → Runnable → Running → Blocked/Waiting/Timed Waiting → Terminated
  • The JVM scheduler maps Java threads to OS threads (1:1 in modern JVM)
  • Synchronization: synchronized keyword uses a monitor lock to ensure only one thread at a time executes a critical section — prevents race conditions
  • Deadlock: two threads each holding a lock that the other needs — circular wait; no progress
  • Java memory model: defines how threads interact through shared memory — visibility, ordering of writes/reads (volatile keyword for visibility)
